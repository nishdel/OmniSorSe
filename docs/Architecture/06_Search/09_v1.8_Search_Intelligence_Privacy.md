# v1.8 Search Intelligence and Privacy

## End-to-end flow

```text
SemanticSearchView
  -> SemanticSearchViewModel
  -> SearchRequest
  -> ISemanticSearchService
       -> ISearchQueryInterpreter
       -> ISemanticIndexStore (compatible JSON candidates)
       -> IProgressiveSearchSource (SQLite-backed candidates/coverage)
       -> ISearchRanker
       -> ISearchSnippetFactory
  -> SearchExecutionResult
  -> visible filters, results, snippets, explanations, and coverage
```

The View and ViewModel contain no SQL, FTS syntax, rank weights, or Ollama
calls. Application contracts describe requests, filters, candidate fields,
ranking components, explanations, snippets, coverage, privacy inspection, and
repair. `OpenSorSe.Indexing.Sqlite` alone owns connections, commands,
transactions, migrations, indexes, WAL lifecycle, backup, and compaction.

## Concurrency and degradation

Search takes a bounded candidate snapshot from the compatible semantic store
and progressive store. The provider serializes each short SQLite operation,
while WAL allows other processes to retain read access according to SQLite's
normal rules. Four Search executions may enter candidate loading/ranking at
once. A waiting or active query observes cooperative cancellation.

The compatible and progressive stores are isolated. If either recoverably
fails, Search uses the other. If deep data is unavailable, filename and
metadata results remain possible. A bounded provider-neutral excluded-path
projection overrides matching legacy entries after an index-only forget without
mixing privacy tombstones into ordinary candidate results. Corrupt optional keyword/vector fields
become absent/incomplete signals rather than partially valid objects.

## Ranking and explanation

`HybridSearchRanker` owns every score contribution. Its tier is the primary
ordering key. Components record the field, signal category, bounded
contribution, plain-language reason, and matched term where safe.
`SemanticSearchHit` carries the same components used to order the result, so
**Why this result?** cannot invent a reason after ranking. Related-concept
similarity is optional, local, and lower than every exact/literal tier.

Snippets are generated only from candidate fields already retained by the
index. They identify filename, path, metadata, document text, OCR, summary,
tag/keyword, or selected-chunk provenance and never reopen a source file.

## Schema 2

`index_privacy_rules` stores source-relative policy:

- excluded;
- optional indexing-level override;
- OCR, summary, and related-concept suppression;
- selected repair stage;
- force-reprocess flag;
- update time.

The source foreign key deliberately preserves manual/watched ownership.
File-forget can remove `index_files` content while retaining the minimum
relative exclusion required to prevent rediscovery and suppress a compatible
legacy Search row. Unexcluding or repair clears only the relevant policy and
reuses the v1.7 durable queue.

## Privacy boundary

Inspection returns category presence/counts and source ownership, not contents
or raw vectors. Forget, clear, and repair operations are transactions over
OpenSorSe-owned derived storage. Original files are never opened for write.
Source verification may read existence before repair but does not mutate it.
Diagnostics use counts, bounded categories, and type names; complete queries
and retained document fields are excluded by default.

Clearing extracted text expands to OCR, summary/keyword, chunk, and
related-concept derivatives. Clearing OCR expands to its downstream generated
representations, and clearing summaries expands to chunks and related-concept
data. Corresponding durable suppression keeps the cleared representation out of
Search until an explicit repair changes that policy. Metadata-only records hide
shared duplicate-derived content even when the shared row remains necessary for
another indexed file.
