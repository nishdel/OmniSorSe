# v2.1 Search and AI quality architecture

**Status:** OpenSorSe v2.1.0 release architecture.

## Preserved ownership

- `SemanticSearchView` binds controls and accessibility metadata only.
- `SemanticSearchViewModel` creates provider-neutral `SearchRequest` values,
  presents outcomes, and routes result actions through desktop interfaces.
- `DeterministicSearchQueryInterpreter` remains the local query/filter parser.
- `HybridSearchRanker` remains the sole owner of deterministic signal tiers,
  scores, explanations, bounded fuzzy matching, and stable ordering.
- `SemanticSearchService` owns query concurrency, candidate-source fallback,
  relationship/graph composition, diagnostics, and optional AI orchestration.
- `IAiSearchAssistant` is the narrow optional application contract.
  `AiSearchAssistant` creates and validates a bounded reranking request.
- `IAiSuggestionProvider` remains the provider-neutral transport boundary;
  `OllamaSuggestionProvider` owns Ollama HTTP details.
- SQLite remains isolated in `OpenSorSe.Indexing.Sqlite`; v2.1 adds no schema,
  query, migration, or provider-specific dependency.

Views and ViewModels do not calculate ranking weights, construct SQL/FTS,
create HTTP requests, or call Ollama directly.

## Deterministic authority

The ranker uses explicit filename full/stem/prefix/substring tiers. Complete
filename-topic coverage is stronger than a weak field match, while a single
filename word from a multi-term query stays in the ordinary literal tier. A
complete literal phrase remains strong. Existing score components and stable
path/file identity tie-breakers remain observable and independently testable.

The adjacent-transposition check executes only inside the existing fuzzy gate:
bounded token lengths, minimum token length, finite fuzzy candidate count, and
cooperative cancellation. It does not expand provider reads or scan source
files.

## AI assistance protocol

`SearchRequest.UseAiAssistance` is explicit. `SemanticSearchService` finishes
deterministic ranking first and supplies only those ranked candidates to
`IAiSearchAssistant`. The assistant:

1. enforces global and Search-specific capability gates;
2. requires a selected model and at least two results;
3. takes at most 12 candidates;
4. maps them to request-local `result-NNN` identifiers;
5. serializes bounded filenames, real match explanations, and existing
   snippets without absolute paths;
6. requests strict schema `search-rerank-v1` at temperature zero;
7. rejects the entire response on any unknown/duplicate ID or invalid shape;
8. reorders only within a deterministic evidence tier;
9. preserves candidate membership and scores;
10. appends an `AiAssistedOrder` component only when a result actually moves.

The application never asks the provider to discover candidates. A failed,
timed-out, unavailable, missing-model, or invalid response returns the original
candidate list. Caller cancellation propagates. Expected transport failures
remain contained; unexpected programming faults are not globally swallowed.

Default Search diagnostics record only the assistance state and bounded
candidate count. They do not add query, prompt, path, snippet, or response text
to ordinary diagnostics. The established explicit unredacted AI-diagnostics
opt-in still governs live prompt/response inspection.

## Ollama discovery

Installed models come from `/api/tags`. A separate two-second best-effort
`/api/ps` request identifies models explicitly reported as running. Runtime
failure does not invalidate installed discovery. External cancellation aborts
both; the short runtime cap avoids making a secondary status affordance delay
normal model discovery. The model-state contract intentionally has only
`Available` and `Running` because no reliable loading state is inferred.

## UI and lifecycle

The Search per-request toggle is disabled until saved settings enable global
AI, Search assistance, and a selected model. Changing saved settings refreshes
the feature state. The view reports the assistance outcome but keeps the normal
Search status/coverage authoritative.

The clipboard command accepts only a result in the current bounded result
collection and uses `IClipboardService`; it does not invoke a shell. Background
indexing is indeterminate only for active run states whose discovered total is
not positive. Known totals continue to use durable monotonic progress.

## Compatibility and tests

All additions are optional properties, enum members, or service dependencies
with compatible defaults/optional constructor positions. Existing requests do
not invoke AI. Existing JSON omits `SearchAssistanceEnabled` and therefore
loads it as false. No index data changes.

Unit and integration coverage verifies filename tier order, phrase conflict,
normalization/transposition, quality metrics, candidate bounding, prompt path
privacy, tier fencing, unknown-ID rejection, provider fallback/cancellation,
service opt-in, Ollama installed/running degradation, settings persistence and
model fallback, indeterminate progress, clipboard routing, and accessible UI
bindings.

The v2.1 manual-validation corrections stay within existing boundaries:
monotonic scan timing belongs to the scan-progress ViewModel; transient
notification dismissal never deletes diagnostics; endpoint locality is a
conservative URI presentation decision; and duplicate removal produces ordinary
`DuplicateAnalysis` MoveFile proposals through `IChangePlanFactory`. Those
moves target the scanner/indexer/watcher-excluded `.opensorse` recovery area,
then use the unchanged validator, executor, Operation Journal, recovery, and
Undo services. No provider, database schema, or migration changes were added.
