# v1.9 relationships, context, and Smart Collections architecture

## Scope

v1.9 adds a bounded, evidence-based relationship projection over the durable
v1.7/v1.8 index. It does not move files, replace Search, create a conversational
assistant, or implement the future knowledge graph. Relationship data is
derived or user-authored application data and can be rebuilt independently.

## Provider boundary

`OpenSorSe.Application.Relationships` owns provider-neutral records and
contracts:

- `IRelationshipEngine` extracts bounded features and creates deterministic
  proposals;
- `IRelationshipStore` persists features, relationships, evidence, collections,
  membership, corrections, diagnostics, and privacy operations;
- `IRelationshipService` coordinates configuration, analysis, inspection,
  manual control, repair, and forgetting;
- `IRelationshipSearchSource` supplies bounded direct expansions to Search.

The desktop View and ViewModel depend only on `IRelationshipService`. They do
not construct SQL, access SQLite, score relationships, or call AI. SQLite is
isolated in `OpenSorSe.Indexing.Sqlite`; another provider can implement the same
contracts without changing Views, ViewModels, or the relationship engine.

## Incremental processing

`RelationshipAnalysisCompleted` remains a durable v1.7 pipeline stage. Its
processor fingerprint now includes the relationship policy and algorithm
configuration. The stage therefore reruns only when the indexed file or a
relevant configuration/version changes, or when the user explicitly requests a
rebuild. A completed unchanged stage is reused by the existing durable job
state.

For one file, analysis performs this bounded flow:

1. load the retained indexed projection;
2. derive and upsert versioned candidate-selection features;
3. query at most the configured candidate bound using indexed feature keys;
4. compare candidates deterministically and cooperatively check cancellation;
5. atomically replace stale automatic edges for the analyzed file while
   preserving manual edges and pair corrections;
6. incrementally refresh eligible automatic Smart Collections and diagnostics.

The engine examines no more than 512 candidates, retains no more than 128
relationships per analyzed file, stores no more than eight evidence items per
relationship, and caps a collection at 2,000 members. These are defensive
ceilings; conservative desktop defaults are lower.

## Evidence and confidence

An automatic relationship is published only from concrete retained evidence:
identical content fingerprints; shared document identifiers; sufficiently
specific filename terms; exact bounded text/OCR/summary fingerprints; shared
accepted tags or generated keywords; corroborating folder/time proximity; and
semantic similarity only when literal evidence also exists. Semantic
similarity alone does not create an edge.

Every evidence row stores a category, a non-content key, and a bounded plain-
language explanation. The explanation shown by the UI is composed only from
those rows. The relationship also stores its algorithm name/version and created
and last-validated times.

Confidence is an enum—Low, Medium, High, or Confirmed—not a fabricated
percentage. Thresholds are deterministic and versioned. Exact duplicate
content or multiple strong independent signals can be High. A user-created or
confirmed edge is Confirmed.

Supported categories are Same Project, Same Trip, Same Purchase, Same Person,
Same Organization, Same Topic, Same Event, Same Version, Same Document Set,
Manual, and Custom. The initial deterministic classifier automatically emits a
conservative subset when evidence supports it; all categories remain available
for explicit user links and future versioned algorithms.

## Smart Collections, context, and timeline

A Smart Collection is a virtual projection. It stores a title, description,
relationship summary, context type, confidence, creation source, timestamps,
pin/rename state, and bounded memberships. It never changes filesystem
location. Automatic suggestions use stable hashed context keys and refresh
incrementally. Forgotten collection tombstones and member-split overrides
prevent immediate recreation.

The collection inspector builds context from stored members and their actual
edges. Its optional timeline is a deterministic ordering of indexed creation or
modification timestamps; labels identify the timestamp source. It does not
infer unrecorded events such as a purchase or flight occurring.

Manual link/unlink, confirm/reject, always/never relate, rename, pin, merge, and
split operations are transactional. Pair overrides survive automatic analysis.
Cyclic edges are permitted as ordinary graph structure, but all queries are
direct and bounded; no recursive graph traversal is performed.

## Search integration

`SemanticSearchService` first performs the v1.8 exact/literal-first ranking.
Only already-ranked file IDs become seeds. When contextual expansion is enabled,
the relationship source returns a bounded set of direct neighbors. Candidates
already in the local Search snapshot receive a `RelationshipContext` ranking
component containing the persisted explanation and optional collection title.

Literal tiers remain above relationship-only and semantic-only results.
Ordering and tie-breaking remain deterministic. The Search checkbox disables
contextual expansion per query. Failure of relationship storage is recoverable:
ordinary filename, metadata, text, OCR, filter, and semantic Search continues.

## Persistence and migration

Embedded schema 3 extends schema 2 transactionally with:

- `index_relationship_features`;
- `index_relationships` and `index_relationship_evidence`;
- `relationship_pair_overrides`;
- `smart_collections`, `smart_collection_members`, member overrides, and
  forgotten-collection tombstones;
- aggregate `relationship_diagnostics`;
- `suppress_relationships` on per-file privacy rules.

The existing migration lifecycle creates a recovery copy before upgrade,
updates the schema version only after all DDL succeeds, verifies integrity, and
rejects unsupported newer schemas. Foreign keys and cleanup rules remove
orphans. SQLite commands are parameterized and disposed. The UI never sees raw
tables or SQL.

## Privacy, security, and repair

The Collections page can forget derived data for a file, source, or collection,
optionally suppress future analysis, and rebuild selected file relationships.
These index-only operations never modify source files or change watched/manual
source ownership. Privacy exclusions are applied to relationship lists,
collection membership/timelines, and Search expansions.

Evidence text is bounded, derived content is not written to ordinary logs, and
aggregate diagnostics use counts/timings rather than paths or document text.
Malformed identifiers, Unicode, enum values, timestamps, semantic vectors, and
oversized input fail closed or are repaired. Candidate, member, evidence, and
Search-expansion bounds prevent relationship explosions. Repair removes orphan
or corrupt derived rows without touching source files.

## Deliberate limits and future work

v1.9 does not perform face recognition, identity resolution, GPS clustering,
recursive archive relationship discovery, learned confidence calibration, or
cross-device graphs. It does not claim every useful relationship will be found.
A future Knowledge Graph may project these versioned evidence edges into richer
navigation, but that remains unimplemented and requires separate privacy,
schema, query, and performance design.
