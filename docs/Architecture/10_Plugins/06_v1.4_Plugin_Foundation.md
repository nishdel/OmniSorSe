# OpenSorSe 1.4 Plugin Foundation

This document is the authoritative implemented plugin architecture for v1.4.
The older files in this directory contain longer-term design ideas unless this
document explicitly includes them.

## Boundary

The public SDK is a dependency-free abstractions assembly. Application owns
manifest parsing, discovery, dependencies, integrity, lifecycle, invocation,
workflow integration, packages, and diagnostics. Desktop owns composition and
the Settings UI. Plugins do not receive the host DI container or mutation,
credential, settings, journal, and approval services.

```mermaid
flowchart LR
    Package["Local ZIP / built-in descriptor"] --> Discovery["Strict manifest-first discovery"]
    Discovery --> Resolver["Compatibility, integrity, dependencies"]
    Resolver --> Runtime["Dedicated collectible ALC"]
    Runtime --> Registry["Conflict-safe contribution registry"]
    Registry --> Host["Bounded extension host"]
    Host --> Workflow["Profile / recipe resolution"]
    Workflow --> Plan["Pending Change Plan proposals"]
    Plan --> Safety["Existing review, preflight, Apply, journal, recovery, Undo"]
```

## Discovery and activation

Discovery inspects only controlled, exact-depth plugin/version directories and
root manifests. It bounds manifests, file trees, count, size, and reparse
points; validates the entry assembly as managed without executing it; and
records invalid/incompatible plugins for inspection. Multiple versions can be
installed, but duplicate identities and contribution conflicts never silently
replace registrations.

Required dependency ranges are resolved deterministically before activation.
Missing dependencies, cycles, version mismatch, incompatibility, integrity
change, disabled state, and quarantine block activation.

External assemblies receive one collectible `AssemblyLoadContext`; the SDK
contracts are shared from the default context. Initialization and stop are
bounded/cancellable and exception-contained. Three repeated startup failures
quarantine a plugin. Unload can require restart.

## Trust and integrity

External plugins start disabled. Enabling explicitly records the accepted
installed hash and granted subset of declared capabilities. Changed content
locks the plugin out. Diagnostics are bounded and redact sensitive fields.

This is defense in depth, not a security sandbox. Plugin code is in-process and
has the operating-system permissions of OpenSorSe. Hashes establish content
identity, not publisher identity. There is no publisher signature authority,
out-of-process worker, marketplace, download, script, or automatic update in
v1.4.

## Extension invocation

All eight extension points use immutable requests, controlled results,
cancellation, timeouts, exception containment, and host validation. Invalid or
oversized results fail atomically. Duplicate providers supply evidence, import
providers supply proposals, and export providers return bytes to the host.

## Workflows, watched folders, and history

Profiles and recipes store stable plugin/version/contribution references.
Resolution produces exact immutable snapshots. Missing capabilities fail
closed with a profile-unavailable state; watched processing cannot substitute a
different plugin. Plugin recipe values include type, derivation, reason,
evidence, and confidence, and all generated actions receive plugin provenance.

Contributions can influence analysis and suggestions only. They cannot mutate
files or approve/apply plans. Template safety, destination validation,
collision policy, review, explicit confirmation, execution, Operation Journal,
recovery, rollback, history, and Undo remain host-owned.

## Built-in references

The four built-in implementations exercise filesystem metadata, extension
classification, a deterministic recipe field, and JSON export. They use the
same SDK/registry/invocation contracts while avoiding external assembly
loading.

## Persistence

`plugins-state.json` stores enabled state, capability grants, accepted hashes,
failure/quarantine state, and selected installed version using bounded atomic
JSON. Missing state is an empty external-plugin configuration. Package files
live below the controlled local application-data plugin root.
