# v2.0 Knowledge Graph compatibility matrix

**Status:** Design target; no v2.0 compatibility claim has been validated yet.

The stable design keeps `deep-index.db` at v1.9 schema 3 and adds independent
graph/decision sidecars. This minimizes change to every existing compatibility
surface.

## Stored-data upgrade and rollback

| Starting application/data | v2.0 design path | Existing data handling | Rollback/downgrade truth |
| --- | --- | --- | --- |
| v1.7 / deep-index schema 1 | v2 retains the existing provider's 1 -> 2 -> 3 migration logic, but release support requires clean frozen schema-1 fixtures, deterministic fault injection, and a reason-pinned verified backup with a committed manifest before migration. Sidecars initialize only after schema 3 validates. | Files, stages, source ownership, content, and settings remain owned by the existing migration; graph stores references/derived projection only. Logical before/after manifests, not SQLite file bytes, establish preservation. | A v1.7 binary cannot read schema 3 after upgrade. Restore only the reviewed, reason-pinned v1.7 pre-upgrade backup; graph or routine rolling backups are not substitutes. |
| v1.8 / deep-index schema 2 | v2 retains the 2 -> 3 migration logic subject to the same frozen-fixture, fault-injection, validation, and pinned-backup gates; sidecars then initialize/import/project. | Search privacy/repair data and v1.8 Search contracts remain. The relationship schema becomes available at schema 3, but relationship data is populated only through normal v1.9 indexing/processing, not merely by migration. | A v1.8 binary rejects schema 3. Restore only its reviewed, reason-pinned pre-upgrade backup. v2 does not claim an in-place downgrade. |
| v1.9 / deep-index schema 3 | Source database remains schema 3 and read/write ownership stays with v1.9 services; an additive `IGraphProjectionSource` exports complete manifests and graph-compatible decisions import idempotently into a non-authoritative mirror. | Relationships, evidence, Smart Collections, overrides, tombstones, Search expansion, privacy, and source ownership are preserved. | v1.9 can reopen schema 3 and ignores `knowledge-graph.db` and `knowledge-decisions.db`; sidecars retain graph settings and decisions for a later return to v2. |
| Fresh v2.0 profile | Existing index initializes through its normal lifecycle; graph remains disabled until informed enablement. | No source file is copied into graph stores. | Removing/disabling graph sidecars leaves existing OpenSorSe features usable. |
| Unsupported newer source/graph/decision schema | Reject the affected store unchanged. | Only features whose own authoritative stores remain healthy and compatible are available. An unsupported deep-index source disables graph projection and its progressive indexed surfaces; independent existing fallbacks may continue. | Install a compatible version or restore a reviewed compatible backup; never silently downgrade. |

## Compatibility surfaces

| Surface | v2.0 requirement |
| --- | --- |
| Original files | Never written, moved, renamed, or deleted by graph operations. |
| Catalogs and saved scans | Existing schemas/APIs remain unchanged and readable. |
| Deep indexing | Existing stages/processor fingerprint remain authoritative; graph has a separate fingerprint and cannot block `FileFullyIndexed`. |
| OCR and AI | Optional as today. Stable graph behavior does not require either dependency. |
| Search | v1.8/v1.9 exact/literal-first ranking and fallback remain; graph expansion is bounded, explainable, and optional. |
| Relationships/Collections | v1.9 IDs, evidence, algorithms, decisions, tombstones, privacy, and direct expansion retain meaning and authority. |
| Watched folders | Existing ownership/reconciliation remains; graph observes but cannot add/remove sources. |
| Duplicate detection | Exact content identity may be projected as Document Set; duplicate algorithms/data are not replaced. |
| Tags | Tag nodes remain experimental/deferred until a provider-neutral tag observation contract supplies stable tag and provenance identity; Search text alone is not tag authority. |
| Workflows/recipes | May supply existing evidence only; graph does not expand execution or approval authority. |
| Plugins/SDK | No stable graph mutation API in initial v2.0. Existing public SDK remains binary/source compatible. |
| Change Plans | Remains the preview/approval boundary for source mutations; graph cannot create an executable bypass. |
| Operation Journal/recovery/Undo | Unchanged and independent of graph state. Graph may observe outcomes only after existing owners commit them. |
| Settings | Graph-only enablement/resource settings live in dedicated lifecycle tables in `knowledge-decisions.db` with conservative defaults. They are not added to the shared typed v1.9 JSON document because v1.9 does not currently guarantee unknown-field round trips. Old settings are not reinterpreted. |
| Diagnostics/privacy | Existing redaction remains; graph adds safe operational facts, inspection, forgetting, and independent retention. |
| Cross-platform | Provider/contracts remain .NET/Avalonia/SQLite compatible; no mandatory OS-specific, server, PostgreSQL, OCR, or AI dependency is added. |

## Manual-decision compatibility

Existing v1.9 manual relationships, pair decisions, collection membership
overrides, rename/pin state, and forgotten-collection tombstones remain in
their authoritative schema-3 tables. The additive `IGraphProjectionSource`
contract exports them as a revision-consistent, completed manifest; existing
relationship operations alone are not a complete import surface. Import into
`LegacyRelationshipDecisionMirror` uses a stable legacy key, manifest ID, and
canonical row hash and never deletes or rewrites the source row. The mirror is
not part of the graph-native authoritative decision sequence.

New `GraphNativeDecision` entity/alias/merge/split/manual-edge decisions live in
`knowledge-decisions.db` and are authoritative only for the new namespace.
v1.9 does not understand them but does not destroy them. Returning to v2
reapplies their ordered sequence.

A v2 command affecting a legacy-owned decision commits through the existing
provider first, then mirrors and projects it idempotently. Mirror failure leaves
the legacy decision authoritative and schedules repair. Only a completed later
manifest may retire a missing mirror row, and retirement is recorded as a
tombstone rather than inferred from an interrupted scan. Conflicts do not use
wall-clock last-write-wins: privacy and explicit rejection are restrictive;
other namespace contradictions become `RepairRequired`.

File/source forget and exclusion use restrictive query barriers so a stale
sidecar cannot override v1.9 privacy state. If the current source or decision
authority cannot be read, graph-derived results and expansion are suppressed;
a stale cache may hide more data but cannot authorize display.

File identity remains source-scoped. A cross-source move creates a new v1.9
file ID and File node. Exact-content evidence may relate the nodes, but does not
silently transfer identity, collection membership, or manual decisions.

## Required compatibility fixtures

Before v2.0 release, clean frozen synthetic schema-1 and schema-2 fixtures must
be created from their version-owned DDL, never by creating the current schema
and dropping newer objects. Checked-in deterministic builders/assets and
expected logical manifests contain no private data. Schema-3 fixtures include
every v1.9 manual-decision/privacy type. Validation covers clean upgrade,
fault injection at every backup/DDL/version/commit/reopen boundary, disk-full,
busy/locked, repeated restart, graph-disabled operation, and rollback to v1.9.

Logical table/schema/invariant manifests establish database preservation;
SQLite file-byte identity is not required because normal WAL/checkpoint/open
behavior can change representation. Original source-file fixtures must remain
byte-for-byte unchanged. Timestamp cursors are never completeness authority:
only a finalized full manifest with terminal count and canonical aggregate hash
may retire unseen rows or advance reconciliation.

No support claim is made until those gates pass on the exact release-candidate
commit.
