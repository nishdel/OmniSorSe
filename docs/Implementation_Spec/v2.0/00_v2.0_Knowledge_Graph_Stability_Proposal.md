# OpenSorSe v2.0 — Knowledge Graph stability proposal

## Status

Design only on `v2.0-knowledge-graph-design`, based on validated v1.9 commit
`7fbc9b47ebf2cd1209c177388aceffe1cb4cec16`. No v2.0 product implementation,
version bump, migration, package, tag, merge, or release is claimed.

## Decision

Proceed with a deliberately small Knowledge Graph release whose primary
objective is isolation and recovery. The graph is a bounded projection of
v1.9 indexed facts, relationships, collections, and explicit decisions. It is
not a new source of truth and never modifies original files.

The design uses:

- unchanged v1.9 `deep-index.db` schema 3 as the source projection boundary;
- a separate rebuildable `knowledge-graph.db` behind provider-neutral
  contracts;
- a separate versioned `knowledge-decisions.db` for irreplaceable user
  corrections that are native to the graph; existing v1.9 relationship and
  collection decisions remain authoritative in schema 3 and are mirrored into
  the graph with explicit provenance;
- crash-safe at-least-once observation ingestion plus a completed,
  stable-primary-key manifest reconciliation instead of a wall-clock cursor or
  a claimed cross-database transaction;
- deterministic conservative identity resolution;
- limited list/detail navigation and bounded Search expansion;
- selective repair before full derived-graph rebuild;
- mandatory release-candidate stabilization before integration/publication.

## Scope classification

| Classification | Capabilities |
| --- | --- |
| Stable enough for v2.0 | File/Source/Folder/Collection/Document Set/manual-entity nodes; typed evidence-backed edges; mechanical exact identity; one-hop navigation; manual corrections; inspection/forget/repair; incremental projection; Search fallback; privacy-safe diagnostics. |
| Experimental, opt-in | Bounded two-hop exploration; Tag nodes after a real tag-observation contract; Project/Purchase/Trip/Organization mention suggestions; Topic/Event or local-model suggestions requiring confirmation. Experimental output cannot auto-merge or become a hidden Search constraint. |
| Deferred | Automatic Person/Place/Event/Topic identity; biometric identity; fuzzy or learned merging; unrestricted traversal/query language; graph canvas; conversation; autonomous actions; remote/cross-device graphs; adaptive learning. |

## Stability rationale

The current v1.9 SQLite store already owns indexing, Search inputs,
relationships, collection membership, privacy, maintenance, and recovery.
Adding graph tables and work to that same database would couple graph locks,
quota, migration, corruption, and rebuild to proven features. A separate
derived store costs an explicit reconciliation boundary but makes failure
containment and rollback testable.

No graph extraction belongs in `FileFullyIndexed`. v1.9 indexing completion is
unchanged. The graph consumes compatible observations asynchronously and may
honestly report partial or stale coverage.

The design also separates four durable state axes: run control, job execution,
component freshness, and component integrity. A coordinator fencing epoch and
per-claim token prevent a reclaimed or shutting-down worker from publishing
late output. Ingestion acknowledgement and component publication use separate
watermarks, so a poison item cannot hide later observations.

Graph reads and graph-backed Search expansion fail closed whenever current
privacy/deletion authority cannot be validated. Ordinary v1.9 behavior remains
available only to the extent that its own supported schema and stores are
healthy; a cached graph snapshot is never evidence that a newer forget or
exclusion decision does not exist.

## Implementation sequencing recommendation

1. Land provider-neutral contracts and fake deterministic stores.
2. Implement the decision ledger with migration/fault-injection coverage.
3. Implement the isolated SQLite graph lifecycle, integrity, backup, and
   unsupported-version behavior without UI.
4. Add projection source paging, durable work states, reconciliation, and
   selective repair.
5. Add conservative entities and typed edges behind a disabled feature flag.
6. Add list/detail inspection and manual controls.
7. Add bounded opt-out Search expansion only after Search regression gates pass.
8. Freeze scope and run a dedicated release-candidate stabilization phase.

Each step must leave existing v1.9 behavior usable. A later step does not waive
an earlier stability gate.

## Explicit release blockers

Any of the following blocks v2.0 integration or publication:

- reproducible loss of v1.9 data or graph user decisions;
- migration or first-run bootstrap without tested interruption recovery;
- an authoritative change detector based only on wall-clock timestamps,
  notifications, or a best-effort cursor;
- conflicting or ambiguous authority between legacy relationship decisions and
  graph-native decisions;
- serving graph results when the current privacy/deletion sequence cannot be
  validated;
- a rebuild that drops merge, split, reject, exclusion, or manual-link intent;
- nondeterministic repeated projection for identical inputs;
- an automatic edge without resolvable evidence;
- unbounded candidate work, traversal, expansion, or operational history;
- stale `Running` work after restart or duplicate active claims;
- a late publisher that can commit after lease loss, cancellation, or shutdown;
- graph failure that blocks indexing or ordinary Search;
- corruption repair that requires deleting `deep-index.db`;
- UI-thread blocking, shutdown hangs, or cancellation regressions;
- private content in default diagnostics;
- graph operations changing an original file;
- skipped tests, policy failures, compiler/analyzer warnings, or unresolved
  critical/high vulnerability findings.

## Release-candidate recommendation

Yes. v2.0 should have a dedicated RC branch/commit after feature freeze. It
should include repeated migration/recovery fault injection, deterministic
rebuild comparison, synthetic large-graph stress, long-running concurrent
Search/index/graph soak tests, all-platform hosted CI, and the fully completed
manual checklist. RC evidence must identify an exact commit; elapsed time or a
working demo is not a substitute.
