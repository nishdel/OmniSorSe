# Project-owner run report — v2.13 catalog cancellation qualification

**Date:** 2026-09-04

**Candidate:** OmniSorSe 2.13.0-rc

**Base:** `main` commit `94013ced55391021d9272fadbd2c8b2feb4b4ea4`

## 1. Objective

Resolve the macOS Intel cancellation/liveness instability that stopped
publication-documentation PR #48 without broadening the v2.13 product scope or
weakening the tests.

## 2. Root cause and correction

Both failed macOS Intel attempts timed out before the blocking comparison double
reported that synchronous comparison work had started.
`CatalogComparisonViewModel` dispatched that work with `Task.Run`, placing it on
the shared thread pool. Under constrained parallel test load, the comparison
start and the asynchronous continuation responsible for requesting cancellation
competed for shared scheduling capacity.

The hosted logs do not expose thread-pool telemetry, so the exact degree of
runner contention is derived from both failures occurring before `Started` and
from the deterministic pre-fix observation that comparison ran on a shared
thread-pool worker. The worker identity, shared scheduling dependency, and
corrected isolation are directly tested.

The ViewModel now dispatches the bounded synchronous comparison through the
default scheduler with `LongRunning` and `DenyChildAttach`, giving it a dedicated
worker. Scheduling itself is not cancelled: the operation token is passed into
`ICatalogComparisonService.Compare`, whose cooperative checks remain the
cancellation authority. This ensures cancellation requested before worker entry
is still observed by the service and keeps UI/test cancellation control
independent of the comparison worker.

No timeout, delay, assertion, bound, service contract, persistence format, or
product behavior was weakened.

## 3. Regression evidence

`CompareAsync_SynchronousComparison_UsesDedicatedWorker` records the executing
thread and fails against the former `Task.Run` implementation because it
observes a thread-pool worker. It passes only when synchronous comparison is
isolated from the shared pool. Existing explicit-cancellation and
selection-change tests continue to verify terminal state and stale-publication
suppression.

Before the implementation change, the new focused regression failed with
`Expected: False; Actual: True`. After the change, all nine Catalog Comparison
ViewModel tests passed, followed by 50 fresh-process repetitions of the complete
class.
